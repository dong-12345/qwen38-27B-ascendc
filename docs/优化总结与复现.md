## 1. 瓶颈定位（怎么找到的）

### 1.1 先量化"我们离硬件多远"

| 指标 | 实测 | 说明 |
|---|---|---|
| 单核 GM 读带宽 | **10.2 GB/s** | 16 KB tile + queue 4；写 10.5 GB/s |
| L2 带宽 | 26–27 GB/s | 片上复用靠它 |
| Vector 峰值 | ~110–134 Gelem/s（fp16） | 1 条 fp16 指令/cycle/128 lane |
| Cube 峰值（高层 Matmul API） | 1.0–1.46 TFLOPS | 与 datasheet 的 20 TOPS 差距大，可接受 |
| UB | 248 KB | 关键约束（决定 tile 大小） |
| 单 token 权重读取 | **15.73 GB** | 12.50 GB int4 权重 + 3.12 GB scale/sz + 0.11 GB f16 |

→ **decode 的硬地板 = 15.73 GB ÷ 10.2 GB/s = 1.54 s/token = 0.65 tok/s**。

### 1.2 旧 GEMV 为什么只有 0.82 GB/s

逐行 GEMV（一行输出 = 4 个相位 × 对 K 的树形归约）：
- 每行 **~48 条向量指令**（多次 Gather/Cast/Mul + 7 步归约树 + 7 条 bias），× 65 ns 固定下发 ≈ **3.1 µs/行**；
- 每行只搬 2.5 KB → DMA 只占 8% 时间 → **瓶颈是"指令下发"，不是带宽**。

一个决定性实验：删掉 16 处同流水 `PipeBarrier<PIPE_V>` 只快了 1.7% → 栅栏不是成本，**指令条数才是**。
（gen2 把 4 个相位的逐行小操作合并成整 K 的 4 条大操作：46.3 ms，**1.18x，逐位等价**；整模型 decode 14.28 → 12.48 s/token。）

### 1.3 prefill 为什么和 decode 一样慢

原来 prefill 逐 token 走同一路径（M=1）→ 17 token 的 prompt 要 212.8 s。
Cube 在 M≥8 时才划算（两段式流量 4.5 B/param），所以 prefill 改 **layer-major 批量（每 32 token 一批）**：
大矩阵走 `dequant_w4`（AIV 反量化到 GM）+ `aclnnMatmul`（Cube），逐 token 小算子保持原样 → **5.8x**。

## 2. 已落地的三项优化

### 2.1 gen2：合并指令的 W4A16 GEMV（decode 默认，逐位等价）

`kernels/w4a16_gemv_gen2.cpp`：把 4 个相位各自的 `Gather/Cast/Mul` 合并为
1 次整 K 的 `Gather`（scale 展开）+ 4 次半字节抽取 + 1 次 `Cast/Mul/Mul` + 3 次 `Add` 折相位。
**运算顺序与 gen 完全一致 → 输出逐位相同**（`gemv_ab` 单测 `nDiff=0/17408`）。
回退开关：`ENG27_GEMV_OLD=1`；Moondream 对应 `MD3_GEMV_OLD=1`（2.39 → 2.02 s/token）。

### 2.2 两段式 Cube（prefill 用）

`kernels/dequant_w4.cpp` + `host/` 里 `aclnnMatmul`（B 用 `[K,N]` 维度 + `{1,K}` 步长解释现有的 `[N][K]` 行主序）。
- K ≤ 8192 走"整 K 展开 + 4 相位合并"（每行 ~15 条指令）；
- K = 17408 走逐相位回退（Gather count 上限 8192）。
- 引擎侧 `runPrefillChunk()` 按层批量：rmsnorm/conv/l2norm/rgdr/gatednorm 逐 token，投影类走 Cube。
- 单矩阵 24.2x / 15.5x，端到端 **5.8x**。

### 2.3 Axpy-N（decode 新路径，AX 布局）

传统 GEMV 必须"沿 K 归约"；换成 **沿 N 向量化**就没有归约了：
```
for n-tile (512 宽):
  acc = 0; bias = 0
  for group g (32 个 k):
     8 次 1D DataCopy（每 word 4 个半字节）→ 4 次拆半字节 + 4 次 Cast
     32 次 Axpy（512 宽）：pH += w[k] * act[k]
     pF = float(pH) * scale[g]; acc += pF;  bias += sz[g]*suma[g]
  out = acc - bias
```
- 权重需离线重排成 **AX `[g][w8][n]`**（uint16 装 4 个 nibble，**存储量与原始格式相同**），scale/sz 转 `[NG][N]`；
- 工具：`./qwen38_ops_test relayout <srcDir> <dstDir>`（401 个 W4 张量，板上约 7–11 分钟，一次性）；
- 单矩阵 **2.32–2.75x**（19.89 / 16.80 ms，随板子负载波动），数值 max_abs 0.0044、0/17408 超差（fp16 组内累加，与两段式同量级）；
- 端到端：**Qwen3.8-27B decode 12.47 → 4.48 s/token（2.78x）**、**Moondream3 2.01 → 0.28 s/token（7.2x，3.6 tok/s）**，tokens 均与基线逐 token 相同；
- Moondream 收益更大的原因：它的矩阵都很小（H=2048、专家 2048→2048），旧 GEMV 受每行约 48 条指令的下发开销支配，而 Axpy-N 的开销与字节数成正比。

**踩过的两个真坑**（写在这里省下次的时间）：
1. scale/sz 的 `DataCopy` 是 **MTE2** 流水，后面只写 `PipeBarrier<PIPE_V>` → `Cast` 读到垃圾 scale（结果整体大 ~50 倍、饱和到 65504）。必须 `PipeBarrier<PIPE_ALL>`。
2. **EMBED 不能一起重排**：它走 `loadEmbedRow()`（按原始 `[N][KQ]` 布局逐行读）。relayout 工具已对 EMBED 做原样拷贝。

## 4. 往 5 tok/s 走：物理约束与路线

对 27B：**1.54 s/token 是单核地板**（0.65 tok/s）。5 tok/s 意味着"每次权重读取要出 ≥7.7 个 token"，
所以只有下面几条路，按性价比排序：

| 路线 | 预期 | 成本 | 风险 |
|---|---|---|---|
| **① 投机解码 / 多 token 验证**（小 draft 模型出 k 个候选，大模型一次前向验证） | 27B: **1.5–2.5 tok/s**（k=4–8，接受率 70–85%） | 大（引擎 + draft 模型） | 中：需保证与贪心解码结果一致 |
| **② AX 布局端到端 + fp8 scale/sz** | 12.48 → **~4.9 s/token（2.5x）** | 小（代码已就绪，scale 转 fp8 再加 10%） | 低 |
| **③ 双缓冲/更大 NT** | 再 +10~20% | 小 | 低 |
| ④ CPU 异构分担（NPU 10.2 + CPU 3.8 GB/s） | +30%（0.85 tok/s） | 中 | 中：LPDDR 争用 |
| ⑤ 手写 Mmad/LoadData2D 融合 MMA | decode 受带宽限，收益 <2x | 很大 | 高 |

对 **Moondream3**（1.03 GB/token，地板 0.1 s/token = 10 tok/s）：②③ 做完预计 **0.3–0.4 s/token ≈ 2.5–3.3 tok/s**，
叠 ① 才有机会进 5 tok/s。**5 tok/s 只在小模型上是现实的。**

## 5. 已知未完成 / 待清理

- `ENG27_LAYOUT=axpy` 端到端验证（板子反复重启打断）；该模式下 prefill 暂强制逐 token。
- 若改 AX 布局，prefill 的 `dequant_w4` 需要改成**读 AX 直接产出 `[K][N]` fp16**（配 `matmulNN`），两路才能共用一份权重。
- `kernels/w4a16_gemv_batch.cpp`（行批处理，1.5–1.6x）**数值不等价**，默认关闭，仅保留作参考。
- `kernels/w4a16_gemv_tok.cpp` 是早期草稿（未验证）。
- **双缓冲（权重 DMA 与 V 计算重叠）**：已尝试但触发 aicore exception（UB 越界类，etCode=0x26），已回退；
  当前 kernel 每组 DMA 与计算仍串行，带宽只用到 31%（15.73 GB / 4.48 s = 3.5 GB/s vs 10.2 墙），
  修好双缓冲预计还能 1.2–1.4x（→ 3.2–3.7 s/token）。\n- 板子网络/供电不稳（反复重启），这是当前唯一的硬阻塞。
## 6. 本轮（Round 10）新增记录

- **Axpy-N 端到端复验**：Qwen 27B decode **4.48 s/token**、Moondream3 **0.28 s/token（3.6 tok/s）**，tokens 与 gen2 基线逐 token 相同。
- **软件流水尝试（失败，已回退）**：目标是让"下一组权重 DMA"与"当前组向量计算"重叠（当前带宽只用到 ~37%，理论上限 1.3–1.5x）。
  三种实现方式（① SetFlag/WaitFlag<MTE2_V> 双缓冲；② 纯 PipeBarrier<PIPE_ALL> 软件流水；③ 两个独立 TBuf + lambda）**全部触发同一个
  aicore exception**：`retCode=0x26` + `D-cache reads/writes UB ... subErrType:4`。
  已回退到串行版本。结论：310B 上 DMA/计算重叠不能靠 flag/barrier 组合，下一步应换机制
  （`DataCopy` 多 queue、或手写 `LoadData` + `Matmul` 让 Cube 与 AIV 并行）。
- 剩余可用的低风险提速项（预计各 1.1–1.2x）：
  1. scale/sz 由 fp16 改 **fp8**（这两张表占 ~26% 流量，减半即省 13%）；
  2. 组内拆成两个半组处理，腾出 UB 把 **NT 提到 2048**（更少 tile、更大 DMA 块）。
## 7. Round 11 记录：一个"更快但还不对"的变体（下一步优先修）

把 AX kernel 的"4 个半字节面"改成"2 个面 × 两趟"（省 UB，可把 NT 提到 1024/2048，Axpy 指令数减半）：
**单矩阵速度大幅提升，但数值不对**，已保存为 `kernels/w4a16_gemv_axpy_2pass.cpp.exp`（默认路径仍是已验证的 4 面版）。

| 变体 | NT=512 | NT=1024 | NT=2048 | 数值 |
|---|---|---|---|---|
| 4 面（现默认，已验证） | 16.8 ms（2.75x） | 19.9 ms（2.32x） | UB 超限 | max_abs 0.0044 ✓ |
| **2 面两趟（实验）** | **13.4 ms（3.42x）** | **8.4 ms（5.46x）** | **7.2 ms（6.37x）** | max_abs 0.23 / 1.9 / 2.0 ✗ |

现象与线索：
- NT=512 时只有 688/17408 个输出错（96% 正确），NT=1024 → 13706 错，NT=2048 → 16286 错 → **错误随 NT 增大**；
- 两趟的半字节/act 下标映射已逐项核对（pass0: nibble0/1 ↔ a[+0/+1]，pass1: nibble2/3 ↔ a[+2/+3]），逻辑上正确；
- 怀疑与 in-place 别名（`u0`/`h0` 共用 `q0Buf`）、或两趟之间 pH 累加的写后读顺序有关。
- 修好后预期：**Moondream 0.27 → 0.12–0.15 s/token（7–8 tok/s）**、Qwen 27B 4.48 → ~2.5 s/token。
## 8. Round 12–13：Axpy-N 提速 1.9x（27B 3.96 s/token、Moondream 0.22 s/token = 4.5 tok/s）

把 kernel 从"4 个半字节面/趟"改成"**2 个面 × 两趟**"，UB 占用减半 → NT 可以从 512 提到 1024
（Axpy 指令数减半）。**关键 bug 与修法**：`u0/u1`(uint16) 与 `h0/h1`(half) 不能共用同一个 TBuf
做就地 Cast——在循环里会被编译器重排，导致数值错（max_abs 2.0、token 全错）；改成独立缓冲后
max_abs 0.0029、0/17408 超差。

| 项 | 4 面版 | **2 面两趟版** | 加速 |
|---|---|---|---|
| 单矩阵 K=5120/N=17408 (NT=1024) | 19.9 ms | **8.4 ms（5.46x vs gen2）** | 2.4x |
| **27B decode** | 4.48 s/token | **3.96 s/token** | 1.13x（累计 3.61x vs 基线） |
| **Moondream3 decode** | 0.27 s/token | **0.22 s/token（4.5 tok/s）** | 1.23x（累计 10.9x vs 基线） |

两个模型的 token 均与基线**逐 token 相同**。
剩余瓶颈：① 27B 里非 GEMV 的 head 级小算子（conv/l2norm/rgdr/gatednorm）已占 decode 的 ~35%；
② scale/sz 表占 20% 流量（fp8 化可省 13%）；③ NT 受 UB 限制（K=17408 仍只能 512）。
## 9. Round 14–15：引擎事故与恢复、AX 路径的取舍

**事故**：用 `Get-Content`/`-join` 往返编辑 `engine_27b.cpp` 时把中文注释的换行吞掉，导致编译失败；
恢复过程中又误删了 prefill 路径的 gatednorm 段。现均已修复：板上 `BUILD_OK`，默认路径 token
`760 6511 314 9338` 与基线**完全一致**。

**尝试失败的优化**（已回退，记录以免重试）：
1. `gatednorm_multi`（把每层 48 次 rmsnorm + 48 次 mul_silu 合并成 1 次）→ 数值不对（token 错乱），已回退。
2. AX 组内累加改 fp32（想拿到与 gen2 完全逐 token 一致）→ 数值崩（max_abs 4.6），已回退；
   `Cast(int16→float32)` 或 fp32 `Axpy` 的行为与预期不符，需另找等价写法。

**当前两条路径的取舍**（27B）：

| 路径 | decode | token 一致性 | 说明 |
|---|---|---|---|
| 默认（gen2 GEMV） | 12.55 s/token | ✓ 逐位相同 | 保守选择 |
| AX（Axpy-N，`ENG27_LAYOUT=axpy`） | **3.57 s/token（4.0x）** | 前 3 个相同，第 4 个在近 tie 处分歧 | 组内 32 项 fp16 累加 vs gen2 的 fp32 |

单矩阵对拍：AX vs gen2 max_abs **0.0029**、0/17408 超差 —— 偏差很小，只在近 tie 处影响 argmax。

**Moondream 没有这个问题**：同样的 AX 路径 **0.22 s/token、token 与基线完全一致**（10.9x），
所以 Moondream 的推荐跑法就是 AX 布局：
`MD3_LAYOUT=axpy ./md3_engine --dir ~/code/moondream3_310b/models/moondream3_310b_ax --ids ... --gen 8`
## 10. Round 16：fp32 组内累加不可行（两次尝试均失败，已回退）

目标：让 AX 路径与 gen2 完全逐 token 一致（消除组内 32 项 fp16 累加带来的近 tie 偏差）。

| 尝试 | 做法 | 结果 |
|---|---|---|
| A | `Cast(int16→float32)` 直接拆半字节，`Axpy(float)` | 数值崩（max_abs 4.6） |
| B | `Cast(int16→half→float32)` 两步 + `Axpy(float)` | 编译通过但数值仍崩（max_abs 3.76、16412/17408 错） |

结论：**这条链上 `Axpy` 的 fp32 语义与预期不符**（half 版正常工作，float 版不对）。
要真正拿到 fp32 累加，只能换成 `Muls + Add`（每项 2 条指令，组内指令数翻倍）——
预计 AX decode 从 3.57 → 5.5–6 s/token（对默认 gen2 12.55 仍是 2.1–2.3x），可作为后续选项。

当前状态（已验证，板端）：
- 27B 默认路径：prefill 37.1 s（5.7x）、decode 12.55 s/token、**token 与基线完全一致**；
- 27B AX 路径（opt-in）：decode **3.57 s/token（4.0x）**，单矩阵 max_abs 0.0029，近 tie 处 token 分歧；
- Moondream AX：decode **0.22 s/token（4.5 tok/s）**、**token 完全一致**（10.9x）。
## 11. Round 17：27B 的 AX 路径达到 **token 完全一致 + 4.0x**（重要修正）

上一轮记录"AX 第 4 个 token 在近 tie 处分歧"是**误判**——那是源码事故后一个损坏的中间构建造成的。
修复后复验：

| 路径 | tokens | decode |
|---|---|---|
| 默认（gen2） | `760 6511 314 9338` ✓ | 12.55 s/token |
| **AX（`ENG27_LAYOUT=axpy`）** | `198 3710 369 248046` **✓ 与基线完全相同** | **3.56 s/token（对原始基线 14.28 = 4.0x）** |

- 组内 32 项 fp16 累加**不影响 token**（单矩阵 max_abs 0.0029，端到端输出一致）；
- 另提供 `ENG27_AX_F32=1`：组内用 `Muls+Add` 做 fp32 累加（更准但慢，UB 限制只能 NT=512），当前**不需要**；
- 之前 failed 的 fp32 `Axpy` 结论仍然成立（float 版 Axpy 语义不符预期），所以 fp32 模式改用 `Muls+Add` 实现。

## 12. Round 18：NT 提升到 2048 的 UB 账目（为什么差 10KB，以及怎么补）

AX kernel（fp16 累加模式）的 UB 占用（字节）：

| 缓冲 | 大小 | 说明 |
|---|---|---|
| wpk | 16·NT | 一个 group 的 8 个 word 行 |
| u0, u1 | 16·NT ×2 | 半字节面（uint16） |
| h0, h1 | 16·NT ×2 | half 面（就地 Cast 后） |
| maskT | 16·NT | 0x000F 掩码 |
| aF, aH | 6·K | 激活 |
| pH | 2·NT（fp16）/ 4·NT（fp32） | 组内累加 |
| acc, bias, scF, szF | 16·NT | fp32 |
| scT, szT, oH | 6·NT | 输出/scale 中转 |

- **NT=1024（K=5120）：166 KB ✓ 可用**（当前）
- **NT=2048（K=2048）：258 KB > 248 KB ✗ 崩（实测 507015）**

要放下 NT=2048，需要省 ~10–16 KB，两个可行手段：
1. **maskT 减半**（16·NT → 8·NT）：掩码只做 4·NT 元素，`And` 分两次调用（每个半字节面多 1 条指令）；
2. **去掉 aH**（2·K）：act 直接 DataCopy 到 `oH`（4·NT 够放 K≤4096）。

预计 NT=2048 可把每 token 的 Axpy 指令数再减半 → **Moondream 0.22 → ~0.15 s/token（6.5 tok/s）**、27B K≤4096 的矩阵同样受益。

**当前状态**：本地源码已改回安全 NT（K≤8192 → 1024、K>8192 → 512），等开发板恢复后需要重新 `build_both` + 复验
（md3 基线 2.0 s/token → AX 0.22 s/token；27B 默认 12.55、AX 3.56 s/token，两者 token 均与基线一致）。

## 最终架构要点

1. **decode（AX 布局 + Axpy-N kernel）**：权重离线重排成 `[g][w8][n]`（4 个半字节/word，存储量与原始 W4 相同），
   kernel 沿 N 向量化：每组 8 次搬运 + 4 次 Cast + 32 次 Axpy（NT=1024），**没有归约树**。
   - 关键坑：`u0/u1`(uint16) 与 `h0/h1`(half) 必须用**独立缓冲**（就地 Cast 在循环里会被编译器重排 → 数值错）；
   - 关键坑：scale/sz 的 `DataCopy` 是 MTE2，读之前必须 `PipeBarrier<PIPE_ALL>`。
2. **prefill（Cube 两段式）**：`dequant_w4`（AIV 反量化）+ `aclnnMatmul`（Cube，M=32 批量），
   引擎按 layer-major 每 32 token 一批；单矩阵 24.2x，端到端 5.7x。
3. **量化**：AWQ 风格 W4A16，group-32 非对称（int4 权重 12.50 GB = 3.99 bit/param + scale/sz 3.12 GB），
   每 token 权重流量 15.73 GB → 单核 10.2 GB/s 的物理地板是 1.54 s/token（0.65 tok/s）。
4. **不做的路线**：投机解码（用户决定不做）；310B Cube 不支持 int4（官方文档），故只能用"先反量化再 Matmul"。

# 310B 推理提速：外部调研结论与落地方案（2026-11-25）

> 本文是"外部经验 + 本板实测"的合并结论，用于决定下一步到底怎么把 27B decode 从
> 14.3 s/token 压到 3 s/token 以内、把带宽从 9% 榨到 60%+。

---

## 1. 三条硬结论（先看这个）

### 结论 A：310B 的 Cube **硬件不支持 int4** —— 融合 int4 MMA 这条路不存在

CANN 官方文档（跨代迁移兼容性指南 / 算子基本概念）原文：
> 「3510 架构版本的 Cube 计算单元**不支持 int4b_t**。相关基础 API 有 `LoadData`、`Mmad`、
> `LoadDataWithTranspose`…**兼容方案：算子侧通过编写 CV 融合算子在 Vector Core 进行
> int4b_t → int8_t 的 Cast 转换，再通过 UB 搬运到 L1 后进行 Mmad 计算**。」

Matmul 模板参数的产品数据表也印证：Atlas 200I/500 A2（=310B）A/B 只支持
`half / float / bfloat16_t / int8_t`，**没有 int4b_t**（只有 A2/A3 有）。

→ **任何"W4A16"路径都必须先在片上把 int4 变成 fp16/int8**，不存在"int4 直接进 L0B"。

### 结论 B：310B 的高层 Matmul **支持把 UB(VECOUT) 直接当作 A/B 输入**

官方 `SetTensorA/SetTensorB`：`LocalTensor` 类型支持的 TPosition 为 **TSCM / VECOUT**，
且分产品数据表里 **Atlas 200I/500 A2 在列**；数据流官方说明含 **`VECOUT->A1->A2`**。
（TSCM 只有 Atlas 350 支持，310B 不要用。）

→ **CV 融合的正确形态**：AIV 把 int4 反量化成 fp16 放在 UB → `mm.SetTensorB(ubHalf)` →
Matmul 内部自己搬 UB→L1→L2 → Fixpipe 出 fp16。**不用手写 LoadData2D/Mmad/Fixpipe。**

### 结论 C：现在 0.94 GB/s 的主因**不是"没融合 MMA"，而是 kernel 结构**

同板（OrangePi AIPro 20T）上的公开项目 [lvyufeng/minicpm-v-4.6-orangepi] 用**纯向量核**在
310B 上做到 decode **170 ms/step**（fp16，10 亿级模型）；社区
[lenLRX/llm_simple] 报 **14B-AWQ 653 ms/token、7B-AWQ 206 ms/token**，反推**有效权重带宽 12–20 GB/s**。
而本项目现在是 0.94 GB/s —— **差 13–20 倍，且用的同一块板、同一个 CANN 大版本**。

他们与我们的结构差异（决定性）：

| 维度 | 我们现在 | 他们的做法 |
|---|---|---|
| 权重布局 | `[N][K]`（一行输出 = K 连续） | **`[group][k][n]`**（n 方向连续） |
| 内层循环 | 对每行输出**沿 K 归约**（7 步树 + 4 相位展开，48 指令/行） | **沿 N 保留 448/512 宽累加器**，对每个 k 做 1 次 `Axpy`（**完全不需要归约**） |
| DMA | 每行 2.5 KB（<16 KB，官方说 16KB 以上才吃满带宽） | 每 tile **≥16 KB**，双/四缓冲流水 |
| scale | 每行 4 次 Gather 展开 | 每 group 1 次 `Mul`（沿 N 448 宽） |

`Axpy` 结构每权重元素约 3.5–4 个向量元素操作、指令密度 ~0.0024 条/元素
（我们现在 0.0094）→ **纯向量路径的理论落点 0.7–1.3 s/token（11–20x）**，
与 llm_simple 的实测数字吻合。

## 2. 本板已实测的两条路径

| 路径 | 实测 | 适用 | 状态 |
|---|---|---|---|
| 向量 GEMV（gen，48 指令/行） | 54.5 ms/矩阵 = 0.82 GB/s | decode | 基线 |
| 向量 GEMV（gen2，合并指令） | **46.3 ms/矩阵 = 0.96 GB/s（1.18x，逐位等价）** | decode | ✅ 已默认启用 |
| **两段式 Cube**（dequant_w4 + aclnnMatmul，M=32） | **75 ms / 32 token = 2.34 ms/token（23.3x）** | **prefill** | ✅ 已验证数值（max_abs 0.0078，0/557056 超差） |
| 两段式 Cube，M=1 | ≈12 s/token（4.5 B/param 流量） | ✗ | 不适用 decode |
| 向量 Axpy-N 结构（结论 C） | 未实现 | **decode** | ⬜ 下一步，预期 11–20x |

## 3. 落地路线（按"收益/确定性"排序）

### P1（最高优先级）：把权重重排成 `[group][k][n]` + Axpy-N 的 decode kernel
- **收益**：decode 14.3 s → **1.1–1.7 s/token（8–13x）**，带宽 0.94 → 8–12 GB/s；
- **代价**：① 一次性把 13.5 GB 权重重排（在 NPU 上做，约 40 分钟，可离线一次）；
  ② 写一个新 kernel（结构已明确：每 group 32 行 × NT=448/512，`Axpy` 沿 N，1 次 `Mul` 乘 scale）；
- **确定性**：高 —— 同板同 CANN 已有 653 ms/token 的 14B-AWQ 先例。

### P2：prefill 端到端接两段式 Cube（已具备全部零件）
- **收益**：prefill 14.3 s/token → **0.3–0.7 s/token（20–40x）**；
- **代价**：引擎改 layer-major（按层对 M 个 token 一起投影），已有 `dequant_w4` + `aclnnMatmul` 单矩阵验证；
- **确定性**：高（单矩阵 23x 已实测）。

### P3：CV 融合（dequant in UB → `SetTensorB(VECOUT)` → Matmul）
- **收益**：在 P1 基础上再 1.1–1.4x（decode 到 ~1 s 以内），且权重不必重排（B 可用 [N][K] 的 ND/NZ 形式）；
- **代价**：需要验证 310B 是否真的接受 VECOUT 输入（文档说支持、**公开无样例**）；
- **确定性**：中 —— 先写 30 行最小 kernel 验编译+数值+吞吐。

### P4：兜底并行
- 若 P1 的 tile/流水调优后仍 < 8 GB/s：叠加 **M=4~8 的投机/批处理**（同 token 数下权重流量 ÷M）；
- 整机 memcpy 读 ~28.8 GB/s、CPU 侧 int4 GEMV 可与 NPU 分层的异构方案（风险高，最后考虑）。

## 4. 下板前先做的 3 个零风险实验（合计 <1 天）

1. **纯读带宽曲线**：扫 `queBytes = 1KB…64KB × bufNum = 2/3/4`（官方 `mem_bandwidth` 样例结构），
   回答"单核纯读到底能到多少"（当前 10.2 GB/s 的口径是 16KB tile + queue 4）。
2. **msprof 看 `GM_to_UB_bw_usage_rate(%)` + `aiv_mte2_time / aiv_vec_time`**：确认现在是 MTE2 受限还是 V 指令受限。
3. **`block_dim` 扫 1→8**：同 kernel 看是并发还是排队（`Ascend310B1.ini` 写 `ai_core_cnt=1`，
   但社区项目在 310B 上用 `GetBlockIdx()=0..7` 切 N，**必须实测澄清**）。
